# Pret helper WebAssembly tools

Yellow Editor compiles the small C helper programs used by the Gen I pret build
pipeline to WebAssembly ahead of time. End users do not need a C compiler in the
browser.

## Current bundle

The web bundle is generated by `scripts/prepare-pret-tools-wasm.mjs` with
Emscripten 4.0.15. It pins the helper sources to a specific `pret/pokeyellow`
commit and verifies each downloaded source file against its Git blob SHA before
compiling it.

The shared Red/Blue and Yellow helper sources are currently byte-identical for:

- `scan_includes`
- `gfx`
- `pkmncompress`
- `make_patch`
- `common.h`

Yellow additionally uses `pcm` for Pikachu audio conversion.

For a normal ROM build, Yellow Editor treats `scan_includes`, `gfx`, and
`pkmncompress` as required for both projects and `pcm` as additionally required
when the checkout contains `tools/pcm.c`. `make_patch` is bundled for the later
Virtual Console patch workflow but is not required for a normal ROM build.

## Generated files

The generated files live under:

```text
public/wasm-tools/pret-gen1/
  manifest.json
  scan_includes.mjs
  scan_includes.wasm
  gfx.mjs
  gfx.wasm
  pkmncompress.mjs
  pkmncompress.wasm
  make_patch.mjs
  make_patch.wasm
  pcm.mjs
  pcm.wasm
```

They are build artifacts and are intentionally ignored by Git. The GitHub Pages
workflow installs the pinned Emscripten SDK, generates the bundle, runs the
`scan_includes` functional smoke test, and then lets Vite copy the bundle into
the deployed site.

To build the bundle locally after activating Emscripten 4.0.15:

```sh
npm run prepare:wasm-tools
```

## Runtime design

`src/core/toolRuntime.ts` defines a platform-neutral command-style tool runtime.
A tool receives arguments plus a set of virtual input files and returns its exit
code, stdout, stderr, requested output files, and elapsed time.

`src/core/pretWasmTools.ts` implements that interface for Emscripten modules. Each
invocation gets a fresh in-memory filesystem, which keeps command-line globals
and `getopt` state isolated between runs.

This interface is deliberately not browser-specific. The same tool invocation
model can later be backed by:

- these WASM modules inside the Tauri WebView, or
- native helper executables invoked by the Rust backend.

The build graph should therefore depend on the shared tool-runtime interface,
not directly on Emscripten.

## Checkout compatibility

The generated manifest contains SHA-256 hashes of the exact helper C/header
sources used to produce the WASM bundle. When a web project is opened, Yellow
Editor hashes the checkout's corresponding `tools/*.c` and `tools/common.h`
files before marking a WASM helper as available.

If pret changes a helper implementation later, Yellow Editor will refuse to
silently use the stale helper module. Updating the pinned source commit/blob SHAs
and rebuilding the bundle is required instead.

## Next build stages

The helper-tool layer does not yet produce a ROM by itself. The remaining web
build work is:

1. add the pinned RGBDS WebAssembly toolchain;
2. mirror the required project files into a shared virtual build workspace;
3. express the Red/Blue and Yellow Makefile dependency/rule graph in shared
   TypeScript orchestration;
4. return the generated ROM bytes through `BuildService`.
